# openedge-xref-mcp

An MCP (Model Context Protocol) server that exposes OpenEdge ABL `XREF`
cross-reference data (generated by `COMPILE ... XREF`) to MCP-compatible
clients such as VS Code / GitHub Copilot Chat.

The actual Python project lives in [openedge-xref-mcp/](openedge-xref-mcp) —
see [openedge-xref-mcp/README.md](openedge-xref-mcp/README.md) for setup,
available tools, and development instructions.

Sample `.xref` data used for testing lives under [examples/.builder/](examples/.builder).

## Using this MCP server in VS Code

Add a `.vscode/mcp.json` file to the project(s) you want to query, pointing at
this server via `uvx` (no local checkout or `uv sync` needed — `uvx` fetches
and builds the package straight from the git repo):

```jsonc
{
  "servers": {
    "openedge-xref": {
      "command": "uvx",
      "args": [
        "--from",
        "git+https://github.com/bfv/openedge-xref-mcp.git@v0.1.0#subdirectory=openedge-xref-mcp",
        "openedge-xref-mcp",
        "--root",
        "${workspaceFolder}"
      ]
    }
  }
}
```

Notes:

- Pin a specific release instead of `main` by appending `@<tag>` to the repo
  URL, e.g. `git+https://github.com/bfv/openedge-xref-mcp.git@v0.1.0#subdirectory=openedge-xref-mcp`.
- `#subdirectory=openedge-xref-mcp` is required because the Python project
  lives in the nested [openedge-xref-mcp/](openedge-xref-mcp) folder, not the
  repo root.
- `--root` is the directory that gets scanned recursively for `*.xref` files.
  Point it at the workspace (or a subfolder containing your compiler XREF
  output); `${workspaceFolder}` resolves to the workspace using this config.
  Alternatively set it via an `env` entry: `"env": { "OPENEDGE_XREF_ROOT": "..." }`.
- After adding the file, open the Command Palette and run **MCP: List Servers**
  to start/inspect `openedge-xref` (or use the "Start" code lens shown above
  the server entry in `mcp.json`).
- If `.xref` files change after the server started, use the `refresh_index`
  tool (or `set_xref_root` to point at a different directory) instead of
  restarting.
- For local development against an unpublished checkout, use `uv run
  --directory /path/to/openedge-xref-mcp/openedge-xref-mcp openedge-xref-mcp`
  as the `command`/`args` instead.

### Offline use / caching

`uvx` caches downloaded packages and git checkouts locally (by default under
`~/.cache/uv`), but that alone doesn't guarantee fully offline runs:

- A tag or branch ref (like `@v0.1.0`, or no ref at all) is *not* immutable, so
  `uvx` still checks the network on every start to see whether it moved. It
  falls back to the cache, but only once the network check has actually
  succeeded at least once.
- A git **commit SHA** is immutable, so `uvx` trusts the cache and skips the
  network check entirely.

For guaranteed offline use, either pin to a full commit SHA:

```jsonc
"git+https://github.com/bfv/openedge-xref-mcp.git@<commit-sha>#subdirectory=openedge-xref-mcp"
```

or add `--offline` to `args` (this fails fast if nothing is cached yet, instead
of silently trying to reach the network):

```jsonc
{
  "servers": {
    "openedge-xref": {
      "command": "uvx",
      "args": [
        "--offline",
        "--from",
        "git+https://github.com/bfv/openedge-xref-mcp.git@v0.1.0#subdirectory=openedge-xref-mcp",
        "openedge-xref-mcp",
        "--root",
        "${workspaceFolder}"
      ]
    }
  }
}
```

Either way, run it once with network access first so `uvx` can populate its
cache before you rely on it offline.
